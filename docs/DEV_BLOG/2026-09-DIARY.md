## 2026-09-18: 1.6.0 — repo-only mods, patch/addon layers, no bottom rail

Three user asks in one session, all verified on the Redmi Note 5 Pro
(Adreno 509) over wireless adb: the mod manager is now 100%
GenLauncher-repository (ModDB deleted), every card carries its own
Update/Delete, and the bottom rail plus the app-bar overline are gone.

### What changed

- **ModDB backend removed.** `ModDbClient`, `ChallengeActivity`,
  `WebViewFetch`, the browse/detail/files screens, `.moddb_meta`
  sidecars and ~40 ModDB strings are deleted; the manifest entry is
  gone too. `GenLauncherReposClient` is the only network source and
  owns its own UA, download stream and 8 GB guard now.
- **Full repository schema.** The index parser reads `ModPatches:` /
  `ModAddons:` per mod (26 mods live), every component manifest yields
  `ModificationType`/`DependenceName`, and updates are pure version
  comparison (`isUpdate`: exact match = current). Fixed a real parser
  bug on the way: patch lists absorbed sibling addon URLs (Shockwave
  showed 13 layers instead of 7) — lists now end at the next sibling
  key.
- **Layers as activation-time merge.** `Mods/<Mod>/<Version>/` stays
  pristine, layers live in `+layers/`, and `resolveLaunchDir` merges
  the enabled set into `+active/` (fingerprinted; no layers = no
  merge, zero behavior change). `mod_launch.cfg` gained a second line
  (pristine base) so selection state survives layers; old one-line
  files still read. Detail page: base Install/Update/Play plus per
  layer Install/Update/Enable/Delete with live re-resolve of a running
  launch on toggle.
- **Per-card Update + Delete.** 2x2 action grid (one row of four
  ellipsized Arabic labels on-device, so it is two rows of two).
  Update opens the page when flagged, else runs a single-family check
  and toasts up-to-date; Delete removes the whole family in one
  confirmed step.
- **GPU recommendation + Vulkan guard.** Advisory chip + one-tap Apply
  (Adreno -> Vulkan, rest -> GLES), warning dialog when Vulkan is
  picked without the OS feature. The tap was exercised on-device and
  exposed a real bug: `onPickRenderBackend` rebuilt `TAB_GRAPHICS`
  (title stuck on "Graphics") — now rebuilds `TAB_HOME`.
- **Chrome removed.** No bottom rail (Home is the page, gear opens
  Settings; slide transition deleted, fade stays), no app-bar
  overline. Back behavior unchanged (detail -> list, Settings -> Home).

### Verification

Local `assembleRelease` (Gradle 9.6.1, same release key) + wireless
install, then screenshot walk: Home (no overline, no rail), GPU chip
"Adreno (TM) 509" + "Recommended for Adreno: Vulkan" + Apply,
installed cards with 4 full-label buttons, Repository tab with live
26-mod index and correct layer counts. No `com.Generals.app` crashes
in logcat. Pre-existing notes: `mergeDexRelease` fails flakily about
once in three local builds (retry succeeds, no code change); the
wireless link flaps under load (reconnect + retry installs).

### v1.6.0 tag: CI signature-gate failure (fixed same day)

The tag build failed at "Verify release signature": `package-android-zh.sh`
ships `assembleDebug`, which is pinned to the in-repo debug key, so the
APK could never carry the release DN the gate greps for (v1.5.0 predates
the gate, which is why it published fine). The script now re-signs with
`apksigner` when signing material exists — validated locally by
re-signing a debug APK and watching the DN flip to the release
identity. Syntax pitfall recorded: apksigner takes
`--ks-pass env:NAME` (space), not `--ks-pass:env NAME`. Tag moved to
the fix commit and CI re-run.

## 2026-09-16: GenLauncher parity — mods as a bottom-nav page, version
## groups, update detection

Both user asks in one: a bottom **Mods page** (the manager as a
first-class tab, not a buried Tools row) and **GenLauncher-style mod
support**. The isolation contract from 09-14 is untouched — every mod
is still its own folder chain under `Mods/`, mounted only via the
engine's `-mod`, retail files never touched.

### What changed

- **`ModsPanel.java` extracted** from the 1,150-line activity: the
  whole manager is now a reusable `LinearLayout` page hosted twice —
  full-screen by `ModManagerActivity` (thin wrapper now, ~90 lines)
  and embedded as Setup's new `TAB_MODS` bottom-nav entry. The panel
  talks to its host through a 3-method interface (launch, request
  folder, activity-result forwarding), which is exactly the seam the
  audit wanted.
- **Version groups** (`ModInstaller.listGroups`): a mod family is one
  row; its downloaded releases expand beneath it, each separately
  selectable/deletable. Downloads now install as
  `Mods/<Mod>/<Version>/` leaves instead of one folder per file,
  matching GenLauncher's version model. Legacy single-folder installs
  read as a one-version family, so nothing breaks on update.
- **Update badges**: each download writes a `<version>.moddb_meta`
  sidecar with the ModDB file-page path. On opening the Mods page the
  panel fetches each family's current release list (paced, one request
  per mod) and badges groups whose installed pages no longer match —
  GenLauncher's "update available" without asking. Manual check
  button + summary toast for explicit runs.
- **Detail page media**: screenshots strip (horizontal gallery,
  ThumbCache-fed) + rating/downloads chips parsed from the profile
  page (`PROFILE_SCREENSHOT` pattern), alongside the existing hero and
  description.

### Engineering notes

- The embedded panel claims a bounded height in `onMeasure` when the
  first measure pass arrives UNSPECIFIED (Setup's ScrollView column
  re-measures with the real viewport right after) — without that the
  inner scrolling page collapses.
- `onBackPressed` is a panel method now: Setup consults it before its
  own Back, the standalone wrapper keeps default activity back for
  the panel's `false` return.
- Known simplification, recorded honestly: a group is "update
  available" when NONE of its installed file pages appear in the
  current release list. For mods that keep old releases listed, no
  badge shows even when a newer file exists — matching installed
  page-ids exactly would need ModDB's file-page date, which the list
  rows don't carry. Good enough for the dominant case (modders
  replace the current release); refine when it bites.

## 2026-09-14: Mod launcher — ModDB browsing, installing, and launching mods

The feature the modding side of the community has asked for the
loudest: the Android app can now browse **every** C&C: Generals Zero
Hour mod on ModDB, download and install them in-app, and launch the
game with one selected — with **zero mixing with the game's own
files**.

### What was already there

The engine has carried a complete `-mod <path>` implementation since
retail (CommandLine.cpp `parseMod` → `GlobalData::m_modDir` →
`ArchiveFileSystem::loadMods()` → `loadBigFilesFromDirectory(TRUE)`):
every `.big` under the mod path is mounted recursively, at
archive-overwrite priority above the retail archives. The port had
simply never exposed it — there was no way to pass arguments on
Android, and no UI to pick a mod.

The gap was therefore glue, not engine work:

1. **Arguments** (`GeneralsMD/Code/Main/SDL3Main.cpp`): on Android,
   read `<internal>/mod_launch.cfg` (one line: the selected mod's
   absolute directory, mirroring the `gamedata_path.txt` marker-file
   convention) and append `-mod <dir>` to argv before `GameMain()`,
   exactly like the existing `-xres`/`-yres` injection. The stock
   parser validates the path itself, so a stale marker degrades to a
   vanilla launch, never a crash. One engine-side fix alongside it:
   `FFmpegVideoPlayer::open()` built mod video paths with a hardcoded
   backslash (`"%s%s\\%s.%s"`), which on Android is a literal filename
   character — every mod-shipped video silently fell back to retail.
   Both copies (GeneralsMD + Core) now use a forward slash, which is
   correct on every platform including Windows. Bink copy noted but
   left alone (not compiled into the Android build).

2. **ModDB client** (`ModDbClient.java`): regex-over-HTML reading of
   the public pages, verified against the live site —
   `/games/cc-generals-zero-hour/mods` (list, `/page/N` pagination,
   `?filter=t&kw=` search), `/mods/<mod>/downloads` (file rows),
   `/downloads/start/<id>` (mirror chooser) and the 302 from
   `/downloads/mirror/...` to the CDN. Desktop User-Agent required:
   the default client gets a Cloudflare challenge page, which is
   detected and reported as "temporarily blocking automated access"
   instead of a parse failure.

3. **Installer** (`ModInstaller.java`): streams the archive to a
   temp file (64 KB chunks, 8 GB cap), extracts **only** `.big` files
   (zip via the JDK, RAR4 via junrar — a large share of ModDB
   releases ship as .rar; nested archives are recursed into), and
   lays them out as:
   `<gameFolder>/Mods/<ModName>/<FileName>/*.big`
   A folder per downloaded file, not per mod, so "Contra 009" and
   "Contra 009 patch" stay separately launchable/deletable. The game
   folder's retail archives are never touched; delete = rmdir -r.

4. **UI** (`ModManagerActivity.java`, entered from Setup → Tools →
   Mods): Installed tab (Play / Delete / Clear Selection, launch card
   with the active mod's name) and Browse tab (search + all-mods
   list, per-mod file list, download confirm + progress). Strings in
   English and Arabic; the mods entry sits on Setup's Tools tab.

### Why this layout and not a merged one

Deliberately the opposite of copying archives into the game folder:

- a mod is removed by deleting one folder — no restore-from-backup
  dance, no risk of leaving a half-copied INI set behind;
- several mods coexist, and vanilla is one button away ("Clear
  Selection"), which doubles as the escape hatch for a bad mod;
- the engine's existing `-mod` semantics (overwrite, recursive) do
  exactly what a mod needs, and the game's own files stay pristine
  for online play and for debugging "is it the mod or the port?".

### Known limits

- `.7z` and `.exe`-installer downloads are refused with a message
  rather than half-installed (junrar covers RAR4 only; RAR5 errors
  out cleanly too).
- ModDB paginates at 30 mods/page and rate-limits aggressive
  crawlers; the client fetches on demand per user tap, which is well
  within that.
- Online multiplayer while a mod is loaded will desync against
  vanilla players — same as PC. Not blocked; just noted here.

## 2026-09-15: Mod launcher professional pass — reliability, detail,
## launch options, self-update

The day-after pass over the mod launcher, from a research sweep of
how GenLauncher (the PC reference), Android's own download
infrastructure, and ModDB's page shapes handle the same problems.
Every phase from the approved plan shipped; nothing was deferred.

### Mod manager completeness

- **Install from device storage** (`ModManagerActivity`): "Add mod
  from storage" opens the SAF document picker; the picked zip/rar/7z
  (or bare `.big`) is staged into the app cache and run through the
  exact same extraction path as a ModDB download. This covers every
  mod that isn't on ModDB — the single biggest functional gap left
  from yesterday.
- **7z support** (`ModInstaller.extract7z`): commons-compress 1.27.1
  added; releases shipped as .7z (previously refused outright) now
  extract like zip/rar. RAR5 remains cleanly refused.
- **Pre-launch validation** (`ModInstaller.validateMod`): before
  writing a mod into the launch path, every `.big` under it is
  checked for the BIGF magic and a plausible directory-table size —
  the same trick the game-folder integrity checker uses. A truncated
  download used to crash the engine mid-INI-load; now the launcher
  shows which file failed and lets the user choose to launch anyway.
- **Crash breadcrumbs** (`AndroidCrashHandler.cpp`): at library-load
  time, if `mod_launch.cfg` selects a mod, `crash.log` records
  `active mod: <path>` next to the build stamp. The first question
  of every crash triage — mod bug or engine bug — is now answered by
  the log itself.

### Reliable downloads

- **Resumable downloads**: archives land in `<name>.part.dl` and a
  retry continues via HTTP `Range` from where the connection died
  (the ModDB CDN honors Range; a refused resume falls back to a
  clean restart, so the worst case is the old behavior). The failed
  install now offers Retry instead of discarding a 90%-complete
  2 GB download.
- **Storage hygiene**: free space is checked before starting (a
  sub-512 MB drive refuses the download before the wait, not after
  it), leftover `.part.dl`/`.extracted` scratch from killed sessions
  is swept on every Mods-screen open with the reclaimed amount
  reported, and each installed mod shows its on-disk size.

### Browse and detail

- **Richer cards**: thumbnails (via a new ~100-line disk+memory
  `ThumbCache` — no image-library dependency), rating and download
  count parsed from the rows we already fetched; every field is
  optional and the card degrades gracefully when the page omits it.
- **Mod detail screen**: tapping a card now shows the profile
  description and hero image before any download; the file list is
  one tap further. Back behaves like a stack (files → detail →
  browse).
- **Sorting + pacing**: popularity/rating/recent/name sorting
  (persisted across sessions), "Load more" pagination instead of
  per-tap page hops, and a 1.2 s pacing gate plus 429/503 backoff in
  `ModDbClient` — ModDB fronts everything with Cloudflare, and the
  burst paths (list → profile → downloads on one tap) could trip a
  soft rate limit that poisons the whole IP for a while.

### Launch experience

- **Fixed resolution** (Setup → Graphics): presets from 800×600 to
  1600×1200, persisted in prefs and written as
  `<internal>/fixed_resolution.cfg`, which the native resolution
  block now prefers over Options.ini (which itself still wins over
  the window-derived size). Height < 600 is rejected natively — the
  engine's UI layouts require it.
- **Launch arguments** (Setup → Graphics, advanced): one argument
  word per line, saved to `<internal>/launch_args.cfg` and appended
  to argv after the `-mod` injection so a user argument can override
  anything the launcher sets. Capped at 16 args natively; comments
  and blanks allowed.

### Self-update

- **In-app update check** (Setup → Help): queries
  `api.github.com/repos/Alaa91H/GeneralsZH/releases/latest`, compares
  the release's versionCode (recovered from the tag via the same
  major*10000+minor*100+patch scheme `build.gradle` documents)
  against the installed one, shows the changelog, and hands the APK
  asset to the system DownloadManager — visible progress, tap to
  install, works only because every build signs with the same fixed
  in-repo key.

### Verification notes

- `:app:assembleRelease` passes (resources, manifest merge, dexing);
  the new Java compiles against the staged SDL 3.4.2 Java tree.
- Native edits touch only the two proven argv-injection blocks plus
  the crash-handler constructor (all stack-buffer C, mirroring the
  `mod_launch.cfg` read that already shipped); the native build is
  validated by the Build Android CI workflow.
- ModDB parsing could not be re-verified against the live site from
  this machine today — Cloudflare is challenging the IP outright
  (a hard block that also affects curl). All new fields are therefore
  defensive-by-construction (nullable, degrade to plainer cards);
  on-device verification remains the real gate.

## 2026-09-16 — Rebrand: "Generals" (com.Generals.app) + tag-driven releases

The launcher stopped carrying the fork alphabet soup in its identity: the
app is now **Generals** under `com.Generals.app`, the Java tree moved to
`com/Generals/app/`, `GeneralsZHActivity` → `GameActivity`,
`GeneralsOnlineActivity/Session` → `OnlineActivity/Session`, the `gzh_`
resource prefix → `gen_`, `Theme.GeneralsZHSettings` → `Theme.Generals`,
and the prefs file `generalszh_setup` → `generals_setup`. Engine and
gameplay files are untouched — this is the launcher/app layer only.

Two consequences handled rather than ignored:

- **New applicationId = fresh private storage.** Android gives the new
  package an empty data dir, so `SetupActivity` runs a one-time
  `createPackageContext` migration: if the legacy app is still installed
  and configured, its game path + mod settings are copied on first launch
  (and mirrored into the native `gamedata_path.txt` marker). The external
  `.generalszh_gamepath.txt` marker still covers the fresh-device case.
- **The crash handler hardcoded the old package.** Fixed by deriving the
  data dir from the process uid (`userId*100000 + appId`) instead of
  hardcoding any name — correct now and after any future rebrand.

Versioning is now tag-driven end to end: pushing `vX.Y.Z` fires the Build
Android workflow, which hands `-PversionTag` to Gradle (versionCode/
versionName derived there, malformed tags fail the build) and publishes
the Release from the same tag. Verified locally: `-PversionTag=v1.4.1`
produced versionCode 10401 / versionName 1.4.1 in the badging output.

Verified: `:app:assembleRelease` passes; aapt badging shows
`package: name='com.Generals.app'`, label `Generals` in all locales.
Deliberately untouched: the macOS bundle ids (`com.generalsx.generalsx*`)
— renaming those would break macOS users' preference paths, and this
rebrand is the Android app's.

## 2026-09-16 — Fixed private release signing key (secrets, never committed)

The release APK had been signed with the committed debug keystore —
convenient (every build updates over the last) but wrong for anything
public: its password is well-known by design and the certificate says
"Android Debug". This pass gives releases their own identity:

- **Key**: RSA-4096, PKCS12, 30-year validity, `CN=Generals, OU=GeneralsX,
  O=Alaa91H`. Generated locally with keytool.
- **Storage**: `secrets/` at the repo root (gitignored — verified with
  `git check-ignore` before anything else). `signing.properties` beside it
  holds the passwords for local builds; `android/app/build.gradle` reads
  env vars first (CI), then that file, and falls back to the debug key
  with the failure mode kept loud rather than silent.
- **CI**: the keystore travels as the base64 `SIGNING_KEYSTORE` Actions
  secret (uploaded via the sealed-box secrets API from this machine), is
  decoded into `secrets/` before Gradle runs, and a new apksigner step
  verifies the packaged APK's certificate DN — a wrong or missing key now
  fails the build instead of shipping an APK that can never update the
  installed one.
- **Verified both paths**: properties-file build and env-var build
  (exactly what CI runs) both produce
  `V2 Signer: certificate DN: CN=Generals, OU=GeneralsX, O=Alaa91H`.

One-time user consequence, documented in the CHANGELOG: builds before
1.5.1 were signed by the debug key, so Android requires a single
uninstall before installing 1.5.1+; every later build updates over the
last, which is the whole point of the fixed key.

## 2026-09-17 — Dead Mods tab solved: an infinite rebuild loop, plus Private-DNS forensics

The test device's Mods tab accepted touches on the shell (app bar, bottom
nav) but every control inside the embedded ModsPanel was dead. Two dumpsys
snapshots 2 s apart showed the entire panel view tree replaced between
them; top showed the app at ~80% CPU; the ART trace (kill -3 ->
/data/anr/trace_02) caught main in performTraversals through
ModsPanel.onMeasure. Diagnosis: an infinite rebuild loop — the auto update
check skipped storage-imported groups (no ModDB origin) without recording
a verdict, `updateByGroup` stayed empty, so every rebuild re-armed the
check, whose completion rebuilt again. Touch died because the view tree
was replaced between every DOWN and UP. Fix: skipped groups record a
verdict; one quiet check per session, like every other path.

Second finding from the same device: with Private DNS set to
dns.adguard.com, `addons.moddb.com` and `image.moddb.com` NXDOMAIN while
`www` resolves — Chrome (own DoH) browses ModDB fine, WebView (system
Private DNS) cannot load challenge assets, and the edge 403s the direct
client. In-app we now (a) trust user CAs via networkSecurityConfig (a
user CA was also breaking WebView TLS with net_error -202), (b) name the
resolver and the fix in the 403 message, (c) require real ModDB markup
before ChallengeActivity declares the challenge cleared (an error page
was being mistaken for success).

Also shipped: the gear page no longer repeats the graphics sections that
live in Home (dedup) — it opens straight to language / text scale / logs /
diagnostics / help. Verified on device: settings clean, Mods tab fully
responsive again.
